## TL;DR
Assignment 1 forced me to implement every component of a supervised learning pipeline in pure NumPy: data loading for MNIST, softmax regression, a two-layer MLP, SGD with L2 regularization, and full training/validation/test evaluation. The deliverable coupled a detailed report (theory problems + paper reviews) with experiments on hyperparameter sweeps, making this the deepest “from first principles” refresher I have done since enrolling in OMSCS.

## Why it mattered
- Re-derived the gradient of the softmax function and the XOR non-separability proof, which anchored the later computational-graph work in the course.
- Implemented forward/backward passes for linear, ReLU, and sigmoid layers plus cross-entropy loss, proving to myself that PyTorch is a convenience, not a crutch.
- Tuned learning rate, weight decay, and hidden width to reach >98% validation accuracy on MNIST while keeping the code unit-testable.

## Representative objective
The full loss combined cross-entropy with L2 regularization across weight matrices:

$$
J(\theta) = -\frac{1}{N}\sum_{i=1}^N y_i^\top \log \hat{y}_i + \lambda \sum_{l} \|W_l\|_2^2,
$$

which my vanilla SGD optimizer minimized via $\theta_{t+1} = \theta_t - \eta \nabla_\theta J(\theta_t)$.

## Introduction: Building the Mental Model Before the Tooling

The first project in a deep learning course is usually where two myths break at the same time. The first myth is that training a model is mostly about choosing a bigger architecture. The second myth is that once the code runs, optimization will naturally produce good behavior. In practice, neither is true. Early project work is where you learn that optimization dynamics are the product, and architecture is only one of the ingredients.

I approached this write-up with the same style as my GIOS and GPU posts: concept-first, failure-mode-aware, and focused on the reasoning patterns I can reuse in future systems work. This is intentionally integrity-safe: no assignment-specific implementation details, no private code excerpts, and no walkthrough of graded solution mechanics.

> [!note]
> The objective of this post is to explain *why* foundational training systems behave the way they do, not to document a specific assignment solution.

## Core Concepts

### Linear Decision Surfaces Are More Informative Than They Look

Linear classifiers are often introduced as a toy baseline, but they remain one of the best tools for understanding optimization behavior. They are expressive enough to expose issues with data scaling, initialization, regularization, and learning-rate policy, while still simple enough that you can reason about every term in the objective.

If we write class scores as `s = Wx + b`, the model is saying: “project input features onto class-specific directions and choose the highest score.” That means every class decision boundary is a hyperplane, and confidence is tied to signed distance from that plane. The geometry matters because it directly maps to training dynamics: poor feature scale means anisotropic curvature, and anisotropic curvature means one learning rate can be too large for one direction and too small for another.

The key lesson is that baseline models are not a formality. They are instrumentation.

### Softmax + Cross-Entropy Gives Probabilistic Semantics and Useful Gradients

The standard multi-class objective combines softmax normalization with cross-entropy loss:

$$
p(y=k \mid x) = \frac{e^{s_k}}{\sum_j e^{s_j}}, \qquad \mathcal{L} = -\log p(y=t \mid x)
$$

The useful property is gradient structure. For class `k`, the derivative with respect to logit `s_k` is:

$$
\frac{\partial \mathcal{L}}{\partial s_k} = p_k - \mathbb{1}[k=t]
$$

That compact term gives immediate intuition: training increases the target class logit and decreases non-target logits in proportion to their predicted probability. When predictions are confidently wrong, updates are large. When predictions are already confident and correct, updates shrink. This is why softmax-cross-entropy remains such a robust default for classification pipelines.

### Backpropagation Is Dependency Accounting Over a Graph

Backpropagation is often explained as “apply chain rule repeatedly,” which is true but incomplete. A more useful systems view is: backpropagation is a reverse dataflow pass that accumulates sensitivity through a directed acyclic graph of operations.

That view clarifies three things:

- Forward pass computes both outputs and cached intermediates.
- Backward pass traverses dependencies in reverse topological order.
- Each node contributes a local Jacobian; upstream gradients are accumulated, not overwritten.

In early projects, most instability bugs are not “advanced ML problems.” They are graph bookkeeping mistakes: silent shape mismatch, stale cache reuse, exploding values from unbounded activations, or poor numerical conditioning in normalization steps.

### Optimization Geometry Explains Most Training Pathologies

SGD-like methods are local geometric procedures. They step in parameter space using gradient direction and a scalar step size. If curvature is uniform and smooth, this works well. If curvature is ill-conditioned, simple updates oscillate across steep directions and crawl along flat directions.

This geometric framing explains recurring empirical patterns:

- Large learning rates can bounce across narrow valleys and never settle.
- Very small learning rates can look stable while making negligible progress.
- Batch size changes modify gradient noise, which can either stabilize or destabilize depending on the regime.
- Weight decay changes effective geometry by shrinking parameter norms and discouraging brittle sharp solutions.

### Regularization Is Capacity Control Under Uncertainty

Regularization is not a single trick; it is a policy decision about what hypotheses the optimizer should prefer when multiple parameter settings fit the training data.

For foundational models, L2 weight decay remains the most interpretable choice:

$$
\mathcal{L}_{\text{total}} = \mathcal{L}_{\text{data}} + \lambda \lVert W \rVert_2^2
$$

The penalty acts like a soft prior against large weights, typically improving validation behavior when data is limited or noisy. But over-regularization is easy: as `\lambda` rises, optimization becomes numerically stable while representational capacity collapses, creating clean but underfit trajectories.

## System/Model Design (abstracted, non-solution-specific)

### Modular Training Architecture

A robust first-principles training pipeline should separate concerns the way production systems do:

1. Data interface and preprocessing.
2. Model forward definition.
3. Loss and regularization composition.
4. Optimizer step and scheduler policy.
5. Evaluation and logging.

This modular split is not style preference. It is what makes controlled ablation possible. If model quality changes after a single modification, you should be able to isolate where that modification entered the pipeline.

### A Generic Training Loop as a Reproducible Protocol

The core loop can be represented without assignment-specific details:

```text
initialize parameters theta
initialize optimizer state
for epoch in 1..E:
  for minibatch (x, y) in training_data:
    y_hat = model(theta, x)
    loss = objective(y_hat, y) + regularization(theta)
    grads = backward(loss, theta)
    theta = optimizer_update(theta, grads)
  evaluate on validation split
  log metrics, schedule state, and checkpoint metadata
```

What matters most in this pseudocode is not the syntax. It is the protocol discipline: fixed data split, deterministic seeds where feasible, and logging rich enough to reproduce conclusions.

### Learning-Rate Policy Is a First-Class Design Choice

In foundational projects, no single hyperparameter has more leverage than learning rate. A useful conceptual decomposition is:

- **Base LR** controls global step magnitude.
- **Warmup** avoids early instability when gradients are poorly scaled.
- **Decay** allows coarse search early and fine convergence later.

## Experiments and Results (sanitized)

### Stable Patterns Across Optimization Regimes

Across runs, several repeatable patterns emerged:

- There is a narrow stability band for LR where both train and validation metrics improve consistently.
- Outside that band, behavior degrades fast: high LR causes oscillatory or divergent loss; low LR produces shallow progress that can be mistaken for convergence.
- The same model can look “good” or “bad” depending on schedule policy, even with identical data and objective.

This is why single-run conclusions are fragile. Optimization policy can dominate architecture effects.

### Why Capacity Increases Often Disappoint at First

Increasing hidden size or depth in early projects often underperforms expectations. That is not evidence against larger models; it is evidence that larger models amplify unresolved optimization issues:

- Poorly tuned LR becomes more destructive.
- Weak regularization enables fast memorization.
- Insufficient monitoring delays detection of drift or overfitting.

A better sequencing strategy is:

1. Lock a stable optimization baseline.
2. Scale capacity incrementally.
3. Re-tune regularization and scheduler policy.
4. Compare under equal compute budgets and seeds.

### Diagnostics That Matter More Than Endpoint Accuracy

Endpoint accuracy is useful but low bandwidth. For debugging and model selection, trajectory diagnostics carry more signal:

- Train vs validation gap over time.
- Loss slope changes around scheduler events.
- Variance across repeated runs.
- Calibration behavior, not only top-1 correctness.

The strongest practical lesson is that model development is a control problem with delayed feedback. If you only inspect final metrics, you lose most of the feedback channel.

## Design Questions This Raised

1. **When should optimization tuning stop and architecture work begin?**  
The practical boundary is not “when loss goes down,” but “when optimization behavior is predictable under small perturbations.” If changing learning rate by a small factor completely changes training outcome, architecture comparisons are still noisy. A strong rule is to freeze architecture changes until the baseline exhibits stable convergence curves, bounded run-to-run variance, and reproducible validation ranking across a small seed set. Once those conditions hold, architecture differences become interpretable instead of confounded.

2. **What defines a baseline that is genuinely decision-useful?**  
A decision-useful baseline has three properties: reproducibility, diagnosability, and extensibility. Reproducibility means another run with the same config lands in the same performance band. Diagnosability means the logging is rich enough to explain failures in terms of optimization behavior rather than guesses. Extensibility means new experiments can branch from the baseline without hidden coupling to one-off code changes. In this sense, the baseline is infrastructure, not just a starter model.

3. **How should regularization be selected when data, compute, and time are all constrained?**  
Regularization should be tuned as a schedule-aware policy instead of a static checkbox. Early in training, mild regularization can stabilize updates and reduce brittle solutions. Later in training, too much regularization can suppress useful specialization and flatten improvements. The practical approach is to define a narrow regularization sweep around a stable learning-rate schedule and compare full trajectories, not just final points. If training and validation both stall, the issue may be over-regularization rather than insufficient model capacity.

4. **Which metrics should gate progress claims in foundational projects?**  
A single metric is rarely sufficient because foundational projects are where miscalibration and instability are most common. A better gating set includes: training objective trend, validation objective trend, task metric trend, and at least one reliability signal such as variance across reruns or confidence consistency. Claims should be written in conditional form: “under this optimization regime and evaluation protocol, model A improved over model B by a reproducible margin.” That phrasing captures both evidence and scope.

<details>
  <summary>Extended reflection: optimization debugging heuristics I would reuse</summary>
  The most useful debugging heuristics from this stage were simple and repeatable. First, inspect gradient magnitude statistics early in training; if they explode or vanish immediately, architecture changes are a distraction. Second, use short controlled runs as diagnostics before launching long experiments. A 5-10 epoch pilot with dense logging often reveals scheduler or regularization issues that a long run would hide until late. Third, compare trajectory shape before comparing endpoints; two runs can end near the same accuracy with very different stability profiles, and the more stable run is usually the better foundation for downstream experiments. Fourth, checkpoint and audit intermediate states rather than only the best final checkpoint. Looking at how representations evolve over time gives stronger intuition for when the optimizer is truly learning versus memorizing. Finally, write down the intended failure criterion before tuning. If “failure” is undefined, tuning becomes open-ended and conclusions get post-rationalized. These heuristics are not specific to a single assignment and generalized directly into later projects in vision, sequence modeling, and generative work.
</details>

<details>
  <summary>Deep dive appendix: practical schedule design under uncertainty</summary>
  Learning-rate schedule design became more intuitive once I treated it as a staged control policy instead of a single hyperparameter. In the first stage, warmup protects against unstable early updates when activations and gradients are still poorly scaled. In the second stage, a moderate plateau allows rapid representation acquisition. In the third stage, decay shifts the optimizer from exploration to consolidation. The exact boundaries vary by model and data regime, but the staged logic generalizes. This framing also clarifies why abrupt schedule changes can produce surprising regressions: the model may not be ready for the next regime when the scheduler transitions.

  Another useful pattern is to pair schedule changes with explicit monitoring triggers. For example, if validation loss slope flattens while training loss continues dropping, it may indicate overfitting pressure and justify earlier decay or stronger regularization. If both losses plateau prematurely, the schedule may be too conservative. These signals are imperfect, but they improve decision quality compared with fixed schedules applied blindly across all experiments.

  The broader takeaway is that schedule policy is part of model specification. Two runs with identical architectures but different schedule behavior can represent meaningfully different systems. Reporting this clearly made my comparisons cleaner and helped avoid attributing schedule-driven improvements to architecture changes.
</details>

## Conclusion

Project 1 established the engineering habits that made later projects tractable: reason in terms of geometry, instrument the training loop, and treat reproducibility as a requirement instead of an afterthought. The key conceptual upgrade was recognizing that optimization policy is part of the model.

The most transferable outcomes were:

- Build analysis hooks before chasing model complexity.
- Use baselines to validate methodology, not just to check boxes.
- Interpret instability through geometry and schedule interactions.
- Make conclusions only from controlled comparisons.

Those four points now act as a gate: if a new experiment plan violates any one of them, I expect noisy results and revise before running.
They also gave me a reusable debugging order: verify gradients, verify schedule behavior, then scale capacity only after convergence is demonstrably stable.

### Practical Checklist I Would Reuse in a New Foundational Project

If I had to restart this phase in a new environment, I would use a strict checklist: validate data scale and label integrity first, run a tiny overfit test to confirm gradient flow, instrument gradient and activation statistics before long training, and define LR schedule policy before architecture sweeps. I would also enforce a report template that includes trajectory plots, not just endpoints, and a short uncertainty note on every comparison claim. This checklist sounds procedural, but it is exactly what prevents wasted compute and false confidence. Foundational projects are where habits are formed, and the highest-return habit is to treat every run as an experiment with explicit controls.

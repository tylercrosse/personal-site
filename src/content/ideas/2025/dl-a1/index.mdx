## The Training Stack in Plain Sight

The first deep learning assignment exposes the mechanics directly. Instead of importing a framework and calling `fit()`, you have to make the pipeline explicit: how scores are computed, how losses become gradients, how gradients update parameters, and how hyperparameters affect learning.

Assignment 1 centers on the small set of concepts that almost every later deep learning system still depends on:

- linear decision surfaces,
- softmax and cross-entropy,
- backpropagation,
- optimization geometry,
- regularization.

The project context is intentionally simple: softmax regression and a small multilayer perceptron in NumPy on MNIST. That stripped-down setting makes each piece of the training stack easier to inspect directly.

> This article is intentionally integrity-safe. The assignment provides motivation and context, but this post does not publish restricted prompts, solution mechanics, or code.

## The Assignment as a System

The assignment builds a supervised learning pipeline from the ground up: load the data, define a model, compute a loss, derive gradients, run optimization, and evaluate the result. The scale is small, but it is exactly where the important abstractions become visible.

Without framework conveniences, a model includes:

- a representation of inputs,
- a loss that defines what counts as a mistake,
- a set of cached intermediate values for the backward pass,
- an optimization policy,
- and an evaluation protocol that tells you whether the run is actually healthy.

The repo work emphasizes verification as much as optimization: unit tests for core pieces, analytical gradients checked against numerical approximations, curve plots across small sweeps, and model selection based on validation behavior instead of trusting the final epoch or one lucky run.

The assignment makes deep learning visible as a system of interacting parts.

## Linear Classifiers Are the Right Place to Start

Linear models look limited, but they are the simplest place to build intuition. If the model computes class scores as

$$
s = Wx + b,
$$

then every prediction is built from a weighted projection of the input onto class-specific directions. The decision boundaries are hyperplanes, and confidence is tied to distance from those boundaries.

<Figure
  src={p1Fig1}
  alt="Loss and decision boundary intuition"
  caption="The geometry of a classifier already tells you a lot about the shape of the optimization problem. Source: Lowyx GT DL Notes (CC BY 4.0), https://lowyx.com/posts/gt-dl-notes/."
  width={900}
/>

This matters because optimization problems are easier to diagnose when the model class is simple. If a baseline linear model fails, the failure is often informative:

- the features may be poorly scaled,
- the learning rate may be unstable,
- the loss may not be aligned with the task,
- or the data may require nonlinear structure the model cannot express.

In this setting, linear models work as instrumentation. They make it easier to tell whether a problem comes from the training setup or from model capacity.

## Softmax and Cross-Entropy Turn Scores into Learning Signal

Scores alone are not enough. A classifier needs a loss that turns "the model is wrong" into a gradient with direction and magnitude. For multiclass classification, the standard move is to turn logits into probabilities with softmax:

$$
p(y = k \mid x) = \frac{e^{s_k}}{\sum_j e^{s_j}},
$$

and then penalize the probability assigned to the correct class with cross-entropy:

$$
\mathcal{L} = -\log p(y=t \mid x).
$$

The derivative is compact:

$$
\frac{\partial \mathcal{L}}{\partial s_k} = p_k - \mathbb{1}[k=t].
$$

That equation explains a lot of training behavior in one line. If the model is confidently wrong, the update is large. If it is already confident and correct, the update shrinks. Softmax plus cross-entropy remains standard because it gives a clean and well-behaved learning signal for classification.

The project made the numerical discipline concrete. Once you compute these terms yourself, details like log stability, normalization, and shape consistency stop feeling like implementation trivia. They are part of the math.

**Illustrative toy snippet, not assignment code:**

```python
import numpy as np

def softmax_cross_entropy(logits, target_idx):
    shifted = logits - logits.max(axis=-1, keepdims=True)
    probs = np.exp(shifted)
    probs = probs / probs.sum(axis=-1, keepdims=True)

    loss = -np.log(probs[np.arange(len(target_idx)), target_idx]).mean()

    grad = probs.copy()
    grad[np.arange(len(target_idx)), target_idx] -= 1.0
    grad /= len(target_idx)
    return loss, grad
```

The point is not the syntax. Stability and gradient shape come from the same design decision: once the logits are normalized carefully, the loss and gradient become simple enough to reason about directly.

## Backpropagation as Reverse Dataflow

Backpropagation is a reverse pass over a computation graph. The chain-rule framing is mathematically correct, but the graph view is more useful in code.

<Figure
  src={p1Fig2}
  alt="Backpropagation graph"
  caption="Backpropagation is easiest to understand as gradient flow through a graph of cached intermediate computations. Source: Lowyx GT DL Notes (CC BY 4.0), https://lowyx.com/posts/gt-dl-notes/."
  width={900}
/>

Each node in that graph does two jobs:

1. produce a forward output,
2. contribute a local derivative during the backward pass.

That viewpoint makes several practical facts clear:

- intermediate values have to be cached somewhere,
- gradients accumulate from multiple downstream paths,
- and a silent shape error can corrupt the whole backward pass.

Implementing the assignment without autograd also makes a common point clear: many "deep learning bugs" are bookkeeping bugs, such as stale caches, wrong broadcast rules, transposed Jacobians, or mismatched tensor shapes.

**Illustrative toy snippet, not assignment code:**

```python
import numpy as np

def numerical_grad(f, x, eps=1e-5):
    grad = np.zeros_like(x)
    for i in range(x.size):
        old = x.flat[i]
        x.flat[i] = old + eps
        plus = f(x)
        x.flat[i] = old - eps
        minus = f(x)
        x.flat[i] = old
        grad.flat[i] = (plus - minus) / (2 * eps)
    return grad
```

A check like this is slow, but it is often enough to tell you whether a backward pass is conceptually correct before you trust a full training curve.

## Optimization Geometry

Once gradients exist, the next question is how parameter updates move through the loss landscape. The simplest mental model is still the right one:

$$
\theta_{t+1} = \theta_t - \eta \nabla_\theta \mathcal{L}(\theta_t).
$$

But that simple rule behaves very differently depending on curvature, scale, and gradient noise.

  src={p1Fig3}
  alt="Loss surface"
  caption="Ill-conditioned loss surfaces explain why some learning rates oscillate while others barely move. Source: Lowyx GT DL Notes (CC BY 4.0), https://lowyx.com/posts/gt-dl-notes/."
  width={900}
/>

Three optimization lessons stuck:

- **Learning rate is not a detail.** It is often the training choice that matters most.
- **Training curves matter.** End-of-run accuracy hides most of the information you need to debug instability.
- **Capacity and optimization interact.** Making the model wider or deeper does not help if the optimization regime is already fragile.

<Figure
  src={p1Fig4}
  alt="Training curve diagnostics"
  caption="Train-vs-validation curves are often the fastest way to tell whether a run is diverging, underfitting, or overfitting. Source: Lowyx GT DL Notes (CC BY 4.0), https://lowyx.com/posts/gt-dl-notes/."
  width={900}
/>

On a project like this, tuning can look small-scale. It is where you learn that a model can fail because the optimizer never reaches a basin that generalizes well, not because the architecture is fundamentally wrong.

## Regularization Picks Among Solutions

Many parameter settings can fit a training set. Regularization is the mechanism that tells the optimizer which kinds of solutions to prefer. In this assignment, the most important version was L2 weight decay:

$$
\mathcal{L}_{\text{total}} = \mathcal{L}_{\text{data}} + \lambda \lVert W \rVert_2^2.
$$

The interpretation is straightforward: the optimizer is penalized for relying on very large weights, which often improves generalization when the model could otherwise memorize brittle patterns.

<Figure
  src={p1Fig5}
  alt="Regularization and generalization"
  caption="Regularization changes the set of solutions the optimizer prefers, which is why cleaner training dynamics do not always mean better generalization. Source: Lowyx GT DL Notes (CC BY 4.0), https://lowyx.com/posts/gt-dl-notes/."
  width={900}
/>

Regularization is not a universal anti-overfitting switch; it changes the search problem. Too little regularization encourages brittle fits; too much regularization makes the run look stable while the model underfits.

That tradeoff showed up immediately in the project. The assignment was small enough that the effect of weight decay and hidden size was visible, but large enough that those choices genuinely changed validation behavior.

## Recap

To recap, here are the main concepts this project focused on:

- **PyTorch hides bookkeeping while leaving the underlying losses, gradients, and updates unchanged.**
- **Baselines are worth taking seriously.** A simple model can tell you a lot about data quality and training stability.
- **Optimization is interactive.** Learning rate, regularization, batch size, and model size do not tune independently.
- **Numerical stability matters early.** Softmax and cross-entropy are easy to write down and easy to implement badly.
- **Training curves carry more debugging signal than final accuracy alone.**

The repo artifacts make those concepts visible: tests for activations, losses, optimizer updates, and network behavior; numerical checks for gradients; and saved plots across learning rate, regularization, batch size, and hidden size. None of that changes the theory, but it does change how quickly theory and implementation drift becomes visible.

It is a foundational assignment in the course because it gives a compact setting where many later deep learning ideas can be traced back to something visible and understandable.

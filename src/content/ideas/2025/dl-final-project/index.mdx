## TL;DR
For the final project our team fine-tuned **Qwen2.5-0.5B-Instruct** on the publicly released s1k reasoning traces and then used Crosscoders—a sparse autoencoder variant—to compare mid-layer activations between the base and fine-tuned checkpoints. We confirmed that scaling test-time reasoning steps improves accuracy on gsm8k and MATH-500, but the Crosscoder showed that the latent geometry at layer 12 remains largely conserved, suggesting downstream utilization changes rather than wholesale feature rewrites.

## What we built
- Training pipeline in LoRA/QLoRA that squeezed 5 epochs of s1k fine-tuning into a 16 GB GPU by capping block size at 2048, enabling a 0.38 final training loss in ~30 minutes.
- Evaluation harness that sweeps chain-of-thought token budgets to estimate *scaling slopes* (accuracy delta per additional 256 generated tokens) on gsm8k, boolq, and math-500.
- Crosscoder atop frozen activations: encoder $B$, decoder $W$, and sparse ReLU features that reconstruct both model states so we can compare which features activate exclusively after fine-tuning.

## Key results
| Dataset  | Model      | Scaling | Accuracy |
|----------|------------|---------|----------|
| gsm8k    | Pretrained | -0.0014 | 41.8     |
| gsm8k    | Fine-tuned | 0.0277  | 51.6     |
| boolq    | Pretrained | 0.0020  | 11.7     |
| boolq    | Fine-tuned | 0.0078  | 10.5     |
| math-500 | Pretrained | 0.0115  | 34.8     |
| math-500 | Fine-tuned | 0.0253  | 48.0     |

We saw the biggest lift on math-500, while boolq slightly regressed—likely because the s1k traces are math-heavy.

## Representative objective
The Crosscoder fits a sparse autoencoder to both activation sets simultaneously:

$$
\min_{W,B} \; \|X - W\,\sigma(B^\top X)\|_2^2 + \|Y - W\,\sigma(B^\top Y)\|_2^2 + \lambda \|\sigma(B^\top X)\|_1,
$$

where $X$ and $Y$ are activations from the base and fine-tuned models, respectively, and $\sigma$ is ReLU. High reconstruction fidelity (>93% cross-entropy recovery) implied that shared features dominate even after fine-tuning.

## Introduction: From Building Models to Understanding Them

The final project changed the question from “How do I maximize task performance?” to “What changed internally when model behavior changed?” That shift is subtle but important. Standard model development is usually output-first: if benchmark metrics improve, we celebrate and move on. Interpretability work adds a second layer: can we characterize *why* behavior changed and how robust that explanation is?

For modern language and reasoning systems, this question is no longer optional. Capability scaling is rapid, but internal mechanism understanding lags behind. A research-oriented final project is a good place to practice making claims with explicit uncertainty and evidence discipline.

## Core Concepts

### Notation and Intuition Snapshot

Let `Z_A, Z_B \in \mathbb{R}^{n \times d}` denote activation matrices from two model variants over matched inputs. I use feature sets `F_A, F_B` for sparse dictionary features and `\Delta\mathcal{B}` for behavior deltas on the same evaluation slices.

### Mechanistic Interpretability as Representation Science

Mechanistic interpretability aims to map internal activations to reusable conceptual features. Instead of treating a model as a black box from prompt to output, it treats intermediate computation as analyzable structure.

In practice, this means asking:

- Which latent features activate for which input patterns?
- Which features are shared across model variants?
- Which features are specific to a finetuned or behavior-shifted model?
- Are observed feature differences stable across data slices?

This is less about extracting a single “true explanation” and more about constructing evidence-backed hypotheses.

### Cross-Model Representation Comparison

Model-diff style analysis compares representations from two related systems (for example baseline vs adapted variant) under matched input conditions. A useful abstraction is feature overlap vs feature specialization.

A central challenge is avoiding superficial correlation claims. If a feature appears model-specific, that does not immediately imply causal relevance to downstream behavior.

### Similarity and Alignment Signals

Representation analysis commonly uses similarity objectives or alignment statistics. A generic template is cosine similarity between normalized feature vectors:

$$
\mathrm{sim}(u, v) = \frac{u \cdot v}{\|u\|\|v\|}
$$

This is useful for measuring proximity in activation space, but similarity is not sufficient for mechanism claims. High similarity can reflect broad shared structure without identifying causal pathways.

For representation-level comparison, centered kernel alignment is often more stable than raw cosine aggregation:

$$
\mathrm{CKA}(Z_A,Z_B)=\frac{\|Z_A^\top Z_B\|_F^2}{\|Z_A^\top Z_A\|_F\|Z_B^\top Z_B\|_F}
$$

Feature overlap can be summarized with a set statistic:

$$
\mathrm{Jaccard}(F_A,F_B)=\frac{|F_A \cap F_B|}{|F_A \cup F_B|}
$$

Derivation intuition: cosine focuses on pairwise direction, while CKA normalizes global alignment and is less sensitive to isotropic rescaling of features.

### Evaluation Beyond Behavioral Benchmarks

Interpretability conclusions require a layered evidence stack:

- Behavior-level changes (task metrics, error profiles).
- Representation-level changes (feature activation patterns, overlap metrics).
- Robustness checks (across prompts, seeds, data slices, and perturbations).

## System/Model Design (abstracted, non-solution-specific)

### End-to-End Interpretability Pipeline

A generic analysis pipeline can be described as:

```text
define comparison pair (model A, model B)
select matched evaluation prompts/tasks
collect activation traces at chosen layers
learn or apply feature dictionary representation
compute feature overlap and specialization statistics
cross-check with behavior-level metrics
run robustness tests and summarize confidence levels
```

This format emphasizes reproducibility and explicit claim boundaries.

A compact claim-confidence scoring rubric I used is:

$$
S_{\text{claim}} = w_b z(\Delta\mathcal{B}) + w_r z(\mathrm{CKA\ shift}) + w_s z(\mathrm{slice\ stability}) - w_u z(\mathrm{uncertainty})
$$

This is not a proof metric; it is a reporting metric to prevent certainty inflation when one evidence channel dominates.

### Data and Prompt Selection Matters

Interpretability findings are highly conditioned on inputs. If prompt coverage is narrow, representation conclusions can be artifacts of slice bias. A stronger approach samples prompt sets across task types and difficulty bands, then checks whether observed feature patterns persist.

### Instrumentation and Logging Requirements

Compared with standard training experiments, interpretability workflows require richer metadata:

- Layer and hook definitions.
- Activation normalization policy.
- Input sampling provenance.
- Post-processing definitions for feature metrics.

Without this metadata, representation claims are hard to reproduce or audit.

## Experiments and Results (sanitized)

### What Representation Comparison Contributed

The strongest contribution of representation comparison was not a single metric gain. It was the ability to generate better hypotheses about *where* behavior differences might come from. In several cases, representation-level anomalies appeared before large behavior-level changes were obvious in aggregate metrics.

That is valuable for debugging, safety analysis, and model selection.

### Where Results Were Fragile

Some apparent findings weakened under broader prompt slices or alternate measurement settings. This fragility is expected and should be treated as signal, not failure:

- It identifies which claims are context-dependent.
- It highlights sensitivity to instrumentation choices.
- It forces confidence calibration in final conclusions.

### Behavior-Representation Agreement

When behavior-level and representation-level signals aligned, confidence increased meaningfully. When they diverged, the right move was to classify conclusions as provisional.

This is the core methodological pattern:

1. Observe candidate feature difference.
2. Test association with behavior change.
3. Stress-test association under perturbation.
4. Assign confidence tier rather than binary true/false judgment.

## Design Questions This Raised

1. **How strong can causal claims be in representation analysis workflows?**  
Without intervention-based tests, causal claims should usually be treated as limited. Most interpretability pipelines in practical settings are correlational: they identify stable associations between activation patterns and behavior differences. Those associations are valuable for hypothesis generation, but they are not proof of mechanism. The right reporting standard is to separate descriptive claims (what pattern appears) from causal claims (what pattern drives behavior) and to communicate confidence accordingly.

2. **What level of validation is enough before publishing conclusions?**  
A useful minimum bar is cross-slice robustness: the claim should survive variation across prompt subsets, seeds, and metric definitions. For higher-confidence claims, include perturbation checks and negative controls that intentionally break the hypothesized mechanism. If a claim collapses under minor protocol changes, it should be downgraded to exploratory status. Validation depth should scale with claim strength.

3. **How should interpretability connect to practical model engineering decisions?**  
Interpretability adds the most value when it changes concrete choices: which model to deploy, which data slice to prioritize, which failure mode to monitor, or which safety check to strengthen. If interpretability outputs never affect decisions, they risk becoming aesthetic analysis rather than engineering evidence. Integrating representation findings with operational metrics keeps the work grounded.

4. **What is the most common reporting failure in interpretability projects?**  
The most common failure is certainty inflation. Visualizations and feature stories can look convincing even when they depend on narrow slices or fragile definitions. A second failure is under-reporting null results. In interpretability work, null results are useful because they constrain hypothesis space and reduce confirmation bias.

<details>
  <summary>Extended reflection: evidence tiers for interpretability claims</summary>
  I found it helpful to classify conclusions into evidence tiers. Tier 1 is observational: a repeatable representation pattern exists under fixed settings. Tier 2 is associative: the pattern tracks a behavior change across multiple slices. Tier 3 is stress-tested: the association survives perturbations and alternate measurement definitions. Tier 4 is intervention-supported: manipulating the relevant feature pathway changes behavior in predicted directions. Most course-scale projects should expect to land around Tier 1 or Tier 2, with selective Tier 3 checks where feasible. This tiering framework improves communication quality because it makes uncertainty explicit and prevents over-interpretation. It also helps prioritize next steps: moving from Tier 1 to Tier 2 often requires broader coverage data; moving from Tier 2 to Tier 3 requires robustness protocol design; moving beyond that requires intervention tooling that may be outside project scope. By organizing results this way, interpretability work becomes cumulative rather than rhetorical.

  Another workflow improvement was maintaining a claim ledger. For each hypothesis, I recorded supporting tests, conflicting tests, known caveats, and confidence tier. This reduced hindsight bias and made final reporting cleaner. It also made collaboration easier because assumptions and boundaries were visible. In future work, I would pair this ledger with lightweight preregistration of key confirmatory checks so exploratory flexibility does not quietly turn into selective reporting.
</details>

<details>
  <summary>Deep dive appendix: practical safeguards against interpretability over-claiming</summary>
  Interpretability projects create a particular kind of risk: explanation fluency can outrun evidence quality. A plot that is visually compelling can trigger strong narrative confidence even when the underlying analysis is slice-dependent or metric-sensitive. To reduce this risk, I found it useful to treat every interpretability output as a candidate claim that must pass explicit checks before promotion. The first check is replication under fixed conditions. The second check is robustness under minor perturbations. The third check is coherence with behavior-level evidence. If any check fails, the claim remains exploratory.

  Another safeguard is to maintain symmetry between positive and negative evidence. If a feature appears to align with one behavior increase, test whether the same feature appears in settings where that behavior does not increase. If negative controls are missing, confirmation bias can accumulate silently. This is particularly important in high-dimensional representation spaces where spurious associations are easy to find.

  I also learned to separate tooling confidence from conclusion confidence. A stable extraction or visualization pipeline does not imply that the resulting interpretation is robust. Tooling stability is necessary because it reduces procedural noise, but interpretation confidence still depends on cross-slice consistency and behavior linkage. Keeping these two confidence notions separate made final reporting clearer and less prone to overstatement.

  A fourth safeguard is scope labeling. Every claim should declare its scope: model family, data regime, task type, and evaluation protocol. Without scope labels, readers may generalize findings beyond what evidence supports. Scope labeling also helps future iterations because it makes it easier to test exactly where a claim breaks when new data or models are introduced.

  Finally, I found that interpretability work benefits from explicit decision hooks. A decision hook is a statement of how a potential finding would change engineering action. Examples include prioritizing a data slice for further curation, adjusting evaluation coverage for a known failure mode, or selecting one model variant over another for safer behavior under uncertainty. If a finding has no plausible decision hook, it may still be intellectually interesting, but it should be reported with appropriately lower practical weight.
</details>

<details>
  <summary>Extended note: connecting interpretability workflows to ML systems governance</summary>
  One broader takeaway from the final project is that interpretability work can function as governance infrastructure when it is integrated early. Governance here does not mean bureaucracy. It means building evidence pathways that help teams reason about why a model is selected, what risks are known, and where uncertainty remains. Representation analysis can contribute to that pathway by surfacing model-specific blind spots and by flagging behavior slices where confidence should be reduced.

  In practical terms, this suggests pairing interpretability outputs with model cards, evaluation dashboards, and incident postmortems. If a model fails on a critical slice, interpretability tools can provide candidate hypotheses for failure mechanism and guide targeted follow-up experiments. This is especially useful in fast-moving model development cycles where retraining is frequent and regression risk is high.

  A second governance-oriented lesson is to preserve audit trails for interpretability conclusions. When claims are tied to explicit datasets, prompts, and measurement definitions, later teams can reproduce or challenge those claims without starting from scratch. This makes interpretability work cumulative across project boundaries, which is essential if the goal is long-term reliability rather than one-off analysis.
</details>

## Conclusion

The final project shifted my perspective from model *performance* to model *evidence quality*. A strong interpretability workflow does not promise perfect transparency. It offers a disciplined way to make and test hypotheses about internal computation.

Most transferable lessons:

- Representation analysis is useful when paired with behavior validation.
- Confidence should be graded, not absolute.
- Robustness checks are part of the result, not optional appendices.
- Interpretability pipelines require the same reproducibility rigor as training pipelines.

That combination turns interpretability from an interesting side analysis into a decision-support capability that can influence real model governance.
It also improves collaboration quality, because uncertainty and claim scope are explicit instead of implicit.

The key operational goal is not to produce the most elegant explanatory narrative, but to produce the most reliable evidence package for high-impact model decisions.
In that sense, interpretability quality is measured less by rhetorical clarity and more by whether independent reviewers can reproduce, challenge, and refine the same conclusions using the documented protocol.
That standard is demanding, but it is exactly what makes interpretability findings useful beyond a single author or a single project cycle.
It also sets the right expectation for future collaborators: claims are starting points for verification, not final truths.
That orientation keeps interpretability work constructive even when findings are partial or contested.
It also reduces the chance of institutionalizing weak assumptions in later model-development cycles.
That is especially important when interpretability outputs are reused in safety and policy discussions where overconfident conclusions can propagate quickly.
Clear protocol discipline helps prevent that failure mode.

### Practical Checklist I Would Reuse in a New Interpretability Study

For future interpretability work, I would enforce a checklist that starts with explicit claim tiers, predeclared robustness checks, and scope labels for every conclusion. I would then require each claim to link to a decision hook explaining why the finding matters for model selection, risk mitigation, or evaluation coverage. Finally, I would maintain a claim ledger with both supporting and contradictory evidence so confidence updates are transparent over time. This checklist keeps interpretability grounded in engineering utility and reduces the risk of narrative overreach from visually persuasive but fragile analyses.

I would additionally require at least one adversarial sanity check per major claim: intentionally alter part of the analysis pipeline in a way that should break the claimed relation. If the claim survives when it should not, the signal may be procedural artifact rather than mechanism evidence. This kind of negative test is common in mature experimental disciplines and fits interpretability work well.

Another carry-forward practice is explicit disagreement logging. When behavior-level and representation-level evidence conflict, the disagreement itself should be documented as a first-class result with candidate explanations and next tests. Treating disagreement as data, rather than as noise to smooth over in the narrative, keeps the work scientifically honest and often points directly to the highest-value follow-up experiments.

I would also preserve a lightweight peer-review step for interpretability reports: before finalizing claims, have someone uninvolved in the analysis challenge scope, evidence sufficiency, and alternative explanations. Even a short review pass can catch certainty inflation and ambiguous language that the primary author no longer sees after many iterations. This is a low-cost control that materially improves claim quality.
